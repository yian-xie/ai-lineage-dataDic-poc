# Skills Validation Report

Validated by following the instructions in `skills/column_lineage_skill.md` and `skills/graph_traversal_skill.md` against the current account graph, HVR metadata, JSON payload contract, HTML contract, and authoritative schema. This is an instruction walkthrough, not a regeneration of lineage outputs.

## Column Lineage Skill

| Step/instruction | Result | Ambiguity or missing information | Suggested fix |
|---|---|---|---|
| Goal: trace every Ultracs field to a Snowflake column and output JSON + interactive HTML | Ambiguous | “Every field” conflicts with the later rule that only evidence-backed mappings are emitted; the current 95 `.param` columns do not all have Snowflake mappings. | Say “Trace every field with sufficient source, `.param`, and downstream evidence; omit unsupported mappings and report coverage.” |
| Inputs: `.param` metadata, account graph, schema, relevant BASIC/inventory files | Clear with caveat | It does not state that the metadata file is generated by `export_hvr_param_metadata.py` or that the account graph depends on `table_lineage.json`. | List prerequisite commands and inputs explicitly. |
| Step 1: load metadata and record position, `.param` name, Snowflake name; do not infer by position | Ambiguous | No rule says how to identify “relevant” mappings or where the Snowflake-column evidence must come from. `.param` names are not generally physical Snowflake names. | Require an evidence citation for each target column and define the selection/omission rule. |
| Step 2: find parent `EXTRACT_FILE` by extract name | Ambiguous | Names may not be unique across source files or graph slices. | Match `type=EXTRACT_FILE` plus extract name and expected `source_path`; fail/report if zero or multiple matches. |
| Step 3: traverse movement edges to physical relation, respect direction, keep branches separate | Ambiguous | It names edge types but does not state their stored directions or how to cross dbt `DEPENDS_ON` and `MATERIALIZES_AS` to reach public relations. | Include the schema direction table and specify reverse traversal for `READS_FROM`/`DEPENDS_ON`; say when relation-level lineage stops at a known gap. |
| Step 4: record `position → .param → Snowflake table → Snowflake column` | Ambiguous | The path omits the BASIC source locator/transformation, route, confidence, and evidence even though other rules require preserving them. | Provide a complete record example and identify which hop is inferred versus confirmed. |
| Step 5: write JSON following `json_payload_skill.md` | Clear with caveat | The linked payload skill says `confidence` is only `confirmed`/`inferred`, but the table-level mapping metadata includes `confirmed_calculated`; no versioning or field requirements are declared for nullable/omitted fields. | Align allowed confidence values across skills and distinguish column payload from `related_columns` metadata. |
| Step 6: write HTML following `html_graph_render_skill.md` | Clear | The render contract specifies graph behavior and styles sufficiently for the referenced generator. | No change required. |
| Focused selector paragraph | Ambiguous | Output filename slug/collision rules and behavior for unknown selectors or duplicate matches are not specified in the skill itself. | State matching precedence, no-match error behavior, collision handling, and that composite selectors can produce multiple records. |
| Rules: confidence, source path, separate routes, no guessed columns | Mostly clear | “Unless the `.param` file explicitly names” a Snowflake physical column is too strict/literal for mappings where `.param` names the source field and dbt supplies a different target name. | Say physical target-column claims require downstream dbt/schema evidence; `.param` establishes the source field name and position, not necessarily the target name. |

## Graph Traversal Skill

| Instruction/query | Result | Ambiguity or missing information | Suggested fix |
|---|---|---|---|
| Forward traversal follows stored direction except reverse `READS_FROM` and `DEPENDS_ON` | Clear | The required exceptions are explicit. The “backward traversal” rule below should be read as reversing the semantic path, not changing graph storage. | No change required. |
| Backward traversal reverses all edges | Ambiguous | It does not define whether a path's edge type is still reported in stored direction or relabeled as a reverse edge. | Require reporting stored edge type plus a separate traversal direction marker. |
| Never cross `is_boundary_node=true`; missing is not true | Clear with caveat | The account graph may omit this property on many nodes, so missing flags mean those nodes are traversable. | Keep the existing rule; optionally list known explicit boundaries in the schema/runbook. |
| Never join direct HVR and S3 routes without evidence | Clear | Matches the current graph's unresolved route boundary. | No change required. |

| Flag inferred hops with reason/evidence | Ambiguous | Some records use `notes` while others use `evidence`; the skill says “recorded reason/evidence” without naming fallback precedence. | Define `evidence` first, then `notes`, otherwise say “no reason recorded” and flag a documentation gap. |
| Show node key, edge type, next key; mark reverse traversal | Clear | Exact output shape is specified. | No change required. |

| Q1: source field to Snowflake | Ambiguous | “HVR route” could mean the separate direct and S3 branches; a column mapping can point to a public relation while the table graph route ends at RAW and dbt model dependencies. | State whether the requested endpoint is RAW, a model's materialized relation, or a public relation; report route and relation-level gaps. |
| Q2: Snowflake table backward to fields | Ambiguous | `COPIES_TO`/`COPIES_FROM` are both stored task-to-path relationships; “reverse applicable movement” does not enumerate which ones to reverse for the semantic journey. | Add a worked account example for load task, Datalake/HVR paths, and stored-vs-semantic direction. |
| Q3: impact of an extract change | Ambiguous | “Every reachable” depends on the same boundary and reverse-edge rules, but there is no required stop condition/count or route-specific output format. | Require separate route traversals, explicit terminal/boundary listing, and a hop table with direction/confidence. |

No changes were made to either skill during this validation. The report separates instructions that can be followed literally from those needing owner clarification or a wording update.
